### 分片上传

分片上传功能，可以将待上传的文件分成多个碎片（`chunk`）分别上传，上传完成之后后端再将这些`chunk`组合成一个完整的文件。

- 使用场景
  1. 网络环境环境不好，存在需要重传风险的场景
  2. 前端请求框架或者nginx设置了单次请求超时
  3. 页面刷新，上传进度丢失

### 实现思路

* [X]  断点续传和秒传
* 断点续传的原理在于服务端需要记住已上传的切片的`md5`值和索引
* 上传前服务端返回已经上传的切片索引，前端跳过这些已经上传成功的切片继续上传
* 文件秒传，需要依赖生成的 `md5`值，即在上传前，先计算出文件 md5
* 后端通过 `md5` 可以判断服务端是否已经上传该文件，从而直接提示用户上传成功（秒传）
* [X]  文件切片
* 核心是利用 `Blob.prototype.slice` 方法，和数组的 `slice` 方法相似，调用的 `slice` 方法可以返回原文件的某个切片
* [X]  生成`md5`值
* 这里用到一个库 `spark-md5`，它可以根据文件内容计算出文件的 `md5` 值
* 另外考虑到如果上传一个超大文件，读取文件内容计算 `md5` 是非常耗费时间的，并且会引起 `UI` 的阻塞，导致页面假死状态，所以我们使用[ `web-worker`](https://blog.51cto.com/u_15315508/5250694) 在 `worker` 线程计算 `md5`，这样用户仍可以在主界面正常的交互
* [X]  上传进度和实时流量
* 原生 `ajax` 的 `onUploadProgress` 事件对切片上传进度的监听
* 上传进度根据总文件大小和已上传分片上传进度计算而来
* 实时上传流量通过计算总上传size，然后每秒生成一次快照。当前size减上一秒size计算而来

### 扩展

计算超大文件md5耗时太长问题

- 思路一（抽样`md5`）
  * 计算文件`md5`值的作用，无非就是为了判定文件是否存在，我们可以考虑设计一个抽样的`md5`，牺牲一些命中率的同时，
    提升效率，设计思路如下文件切成2M的切片第一个和最后一个切片全部内容，其他切片的取首中尾三个地方各2个字节合并后的内容，
    计算出抽样`md5`的结果。缺点是有小概率误判，但是可以大幅减少全量计算`file`的`md5`时间。<br/><br/>
